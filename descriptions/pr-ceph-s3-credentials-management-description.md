# Summary

Gives Ceph/S3 users a place to see and manage their own access keys. Reported from `dashboard-aurora.eu-de-1.cloud.sap`, on the bucket list of a project that already had a working key:

> I have no option to see or manage my credentials.

There was no such screen. The only credentials UI in the product was `CredentialPrompt`, and `CephBuckets` rendered it on exactly one condition — `errorMessage === "NO_CEPH_CREDENTIALS"` — so a user who had a key could never reach it again. It was also the one place a secret was ever produced, and it threw it away: the `create` mutation already returned `{ access, secret }`, the component invalidated the list and called `window.location.reload()`, and the secret went with the page. A user who missed that moment, or who arrived after someone else set the project up, had no way to recover it and no way to rotate.

**The secret was recoverable all along.** Keystone's EC2 credentials are not Application Credentials: the secret is stored encrypted but decrypted on every read, so `GET /v3/credentials?user_id=…&type=ec2` returns a `blob` containing both halves, and the default `admin_or_owner` policy lets the owner read their own. Aurora's own BFF has relied on this since Ceph support landed — `resolveEC2Credential` (`middleware/resolveEC2Credential.ts`) performs that exact read on every Ceph request to sign the S3 call. Nothing new had to be exposed; the data was already crossing the BFF several times per page.

**Why a secret is fetched only at the moment it is revealed.** Each secret sits in Juno's `SecretText`, which conceals by drawing a blurred cover (`juno-secret-cover`, `backdrop-blur`) over a `<textarea>` that still holds the value — the concealment is paint, not absence. Filling every field as the modal opens would therefore put every key the caller holds into the DOM behind something that is not a boundary, on behalf of a user who most likely opened the modal to copy an endpoint. `handleRevealSecret` (`ManageCredentialsModal.tsx:208`) is wired to the component's own Reveal instead, so a secret enters the page only when somebody asks for it and the cost is one request per key actually opened rather than one per key that exists. `requestedSecretIds` holds it to one: hiding leaves the value in component state, so the toggle is free from then on, while a failure releases the id again so the next Reveal is a retry and not a no-op against a poisoned entry.

**Why the key you sign with was previously arbitrary.** `resolveEC2Credential` picked its credential with `.find()` over whatever order Keystone returned. With one key that is invisible. This PR allows two, so it became worth defining: the list is now sorted by credential `id` (`resolveEC2Credential.ts:63`) and the choice is stable across requests. EC2 credentials carry no timestamp, so this is deterministic rather than "most recent" — there is still no concept of an active key, and all of a user's keys map to one RGW identity anyway.

**Why one missing policy rule used to hide an entire domain.** `createPermissionRouter`'s `canUser` evaluates every requested key through `.map`, and `policy-engine` throws a plain `Error` when a rule is absent from the loaded file and that file has no `_default`. An uncaught throw therefore failed the whole batch — and `useCephPermissions` asks for ~20 keys in one call, so a single unknown rule hid every action in Ceph, not the one it governs. That is a reachable state and not only a mistake: `policyDir` is a consumer-supplied `createServer()` parameter, so operators run their own policy files, and a file written before a newly added key simply will not have that rule. Adding `storage:credentials:delete` would have walked straight into it. `checkSinglePermission` now catches that one failure per key and answers `false` for it alone (`createPermissionRouter.ts:156-166`); every other error still propagates, because answering "no permission" to a malformed rule expression would turn a real fault into a plausible-looking UI with no signal anywhere.

# Changes Made

## Server

- **`ec2CredentialRouter.ts`** — new `reveal` mutation (`:241`), returning `{ id, access, secret, user_id, project_id }` for one credential. A mutation and not a query on purpose: a query result lands in the TanStack Query cache and outlives the modal, visible in devtools until garbage collection, whereas a mutation result is never cached and is dropped by `reset()`.
- **`ec2CredentialRouter.ts`** — `fetchOwnedCredential` (`:59`), shared by `reveal` and `delete`. Both `user_id` and `project_id` come from the rescoped token, never from input; a credential the caller does not own is answered `NOT_FOUND`, not `FORBIDDEN`, so this check's own answer cannot confirm that an id exists (the anti-enumeration property added in #1182, previously implemented inline in `delete`). Credentials of any other `type` are reported the same way a missing one is, rather than being deleted or parsed as an EC2 blob by a router that presents itself as S3 key management.
- **`ec2CredentialRouter.ts`** — `create` enforces a ceiling of two credentials per (user, project) with a pre-check that fails closed: if the count cannot be established, creation is refused rather than allowed (`:189-190`, `CONFLICT` / `EC2_CREDENTIAL_LIMIT_REACHED`). Two mirrors AWS's own limit — enough to rotate without downtime, not enough to accumulate keys nobody can account for.
- **`ec2CredentialRouter.ts`** — `delete` is genuinely idempotent now. `signal-openstack`'s `request()` rejects with `SignalOpenstackApiError` on every non-2xx instead of resolving with `ok: false` (`packages/signal-openstack/src/client.ts:194-207`), so the `if (!response.ok)` branch that was supposed to absorb a 404 was unreachable and deleting an already-deleted credential answered `NOT_FOUND`. The 404 is now caught where it actually arrives.
- **`helpers/ec2CredentialMapper.ts`** — new. `toEc2Credential` / `toEc2CredentialWithSecret` replace the parse-and-validate block that stood three times in the router. Stricter than what it replaces: `"null"`, `"42"` and `"[]"` are valid JSON and used to reach the field reads, where `null` threw a `TypeError` the surrounding `try` swallowed by accident. Error messages name the credential id and nothing out of the blob.
- **`containerRouter.ts`** — `containers.status` returns `endpoint` and `region` alongside `hasCredentials` (`:36-37`). The S3 endpoint and region were known only to the server (`cephProcedure.ts`'s `resolveS3Config`) and appeared nowhere in the UI, which makes an access key on its own unusable. The procedure stays on `cephProcedure` rather than `cephProtectedProcedure` so Connection Details renders for a user who has no key yet.
- **`resolveEC2Credential.ts`** — sorts by `id` before choosing (`:63`), as above.
- **`policies/createPermissionRouter.ts`** — the per-key catch described in the summary. Matched on `policy-engine`'s message because the engine throws a plain `Error` and offers no way to ask whether a rule exists; logged at `warn` rather than `error`, since the docblock calls this a legitimate deployment state and ~20 keys are checked per page load.
- **`types/ceph.ts`** — `s3StatusSchema` gains `endpoint`/`region`; the four EC2 input schemas collapse into one `ec2CredentialIdInputSchema` used by both `reveal` and `delete`. Three of the four had no reference outside this file, `delete` re-declared its input inline, and the test suite was exercising the copy production never evaluated.
- **`routers/permissionRouter.ts`**, **`apps/dashboard/src/policies/storage.json`** — new permission key `storage:credentials:delete` → `storage:credential_delete`, viewer-tier for the same reason as `create`: managing one's own access keys is self-service, and Keystone enforces ownership independently.

## Client

- **`Ceph/Credentials/ManageCredentialsModal.tsx`** — new. Each key the caller holds in the project gets a `Box` of its own (`:356`): the access key ID in full in the header, since Keystone's credential object carries no name or label and that string is the only way to tell two keys apart, with the delete button beside it, and a `SecretText` beneath. A card rather than a `DataGrid` row because `SecretText` is a ~120px textarea with its own button row, which a table can only accommodate by growing every row to match and putting a form control inside a cell — and with a ceiling of two keys the grid was buying column alignment for two one-line values, one of which is no longer one. `readOnly` (`:389`) is what drops the component's Clear and Paste buttons, leaving Reveal/Hide and Copy; Copy disables itself while the value is empty, which it is until the fetch lands. The modal is `size="large"` (40rem, `:259`) — the previous `xl` existed for the three-column table and only stretched a textarea nothing fills. Connection Details carries the endpoint and region, each copyable on its own. Creating a key shows its secret immediately, with no page reload, in a field that comes up already revealed (`newlyCreatedIds`, `:88`) and spends no `reveal` request doing it, since `create` returns the value itself; a toast names the new access key and where to find it again. That second sentence is the useful half: the very first key in a project is created from the empty state by someone who has never seen this modal and reached it through a menu they had no reason to open, so without a pointer back the modal is found by accident and the secret reads like a one-time reveal. Deleting is a single click on the card's trash button, matching how a row is removed from the metadata tables that live inside modals elsewhere in the dashboard; a spinner replaces the button while the request is in flight and a toast names the deleted key afterwards.
- **`ManageCredentialsModal.tsx`** — secrets live only in component state. `list` still strips them server-side, so nothing puts one in the query cache, and closing the modal clears them in every path. A completion that lands after a close is dropped rather than written back (`isOpenRef`), and the per-opening bookkeeping is reset on the way *in* as well, because Escape reaches Juno's `Modal` through its focus trap's `escapeDeactivates`, which consults only `closeable`/`closeOnEsc` and ignores `disableCancelButton`/`disableCloseButton`. `closeOnEsc={!isBusy}` (`:268`) stops Escape from running the close handler ahead of a pending mutation's own callback. `isBusy` deliberately excludes the secret fetches (`:166`) — those belong to one card's Reveal, and a failed one is reported as that field's own `errortext` rather than as the modal-wide error `Message`, so one key going wrong neither blocks Close/Create/Delete nor obscures the other key.
- **`Ceph/hooks/invalidateCredentialQueries.ts`** — new, third in the family after `invalidateBucketQueries` and `invalidateVersioningStatusQueries`. Refreshes the key table on every mutation and the bucket listing only when the project crosses between "no keys" and "at least one", which is the only transition `containers.list` reacts to — it is read with `includeMetadata: true`, the router's documented slow path, one `ListObjectsV2Command` per bucket in batches of five. The decision is taken from the cache *after* the credential list has been refreshed, not from the caller's copy: during a rotate the second mutation can settle before the first one's refetch lands, and a listing left in its `NO_CEPH_CREDENTIALS` error state with `retry: false` never refetches on its own. `containers.status` is deliberately not invalidated — its only reader takes two deployment constants from it under `staleTime: Infinity`, and each refetch would cost a Keystone credentials lookup in `cephProcedure`'s middleware.
- **`Ceph/Buckets/index.tsx`** — two entry points, both into the same modal: the overflow menu beside "Create Bucket" (`:328`), and the rewritten empty state. A third was added to the previously dead-end "invalid credentials" error branch, which offered prose and nowhere to go. The modal is mounted from a single unconditional return alongside `content` (`:226-238`) rather than after the early returns, because deleting the last key from inside it flips the page underneath into the `NO_CEPH_CREDENTIALS` branch and the modal has to survive that transition instead of unmounting mid-operation.
- **`Ceph/Credentials/CredentialPrompt.tsx`** — moved here from `Ceph/Buckets/`, and no longer creates a credential or reloads the page; it opens the modal. `CredentialToastNotifications.tsx` holds both toasts, created and deleted.
- **`Ceph/hooks/useCephPermissions.ts`** — adds `canDeleteCredential` → `storage:credentials:delete` (`:68`). Reads stay ungated, per the hook's own docblock; only the two mutations are gated, and a failed permission *query* is now told apart from a denial, so a user is not advised to contact an administrator about access they already have.

# Testing Instructions

1. `pnpm i`
2. `pnpm run test`
3. Open a project with Ceph object storage, `/projects/<id>/storage/ceph/containers`.
4. **With no keys yet:** the empty state reads "S3 Object Storage: Setup Required" and its button opens the modal instead of silently creating a key and reloading. Create one — its secret appears immediately, in a field that is already revealed rather than concealed, a toast names the key and points back at "More Actions", then "Manage Credentials", and the bucket list behind the modal fills in once you close it.
5. **With a key:** open the overflow menu beside "Create Bucket", then "Manage Credentials". Each key is a card with its access key ID and a concealed secret; Connection Details shows the endpoint and region. Press Reveal on one key — only that secret is fetched (check the network tab: one `reveal` call, none for the other key), Copy becomes usable, and Hide/Reveal again costs no further request. Every value copies on its own.
6. Verify a key actually works: `AWS_ACCESS_KEY_ID=… AWS_SECRET_ACCESS_KEY=… aws --endpoint-url <endpoint> --region <region> s3 ls`.
7. Create a second key, then confirm "Create Access Key" is disabled and the section text explains the limit of two. A direct third call to `storage.ceph.ec2Credentials.create` answers `CONFLICT` / `EC2_CREDENTIAL_LIMIT_REACHED`.
8. Delete one of the two — the card goes, a toast names it, and the bucket list is *not* re-scanned. Delete the last one and the page behind falls back to the empty state.
9. Press Escape while a create or delete is in flight: the modal stays open until the request settles.
10. Operators with a forked `storage.json`: add `"storage:credential_delete": "rule:storage_viewer"` (or an equivalent). Without it the Delete action stays hidden and one `warn` line per check names the missing rule — the rest of the Ceph permissions are unaffected, which is the `createPermissionRouter` change above.

# Behaviour and Contract Changes

- New procedure `storage.ceph.ec2Credentials.reveal`.
- `storage.ceph.ec2Credentials.create` can now fail with `CONFLICT` (`EC2_CREDENTIAL_LIMIT_REACHED`).
- `storage.ceph.containers.status` returns two additional fields. Purely additive for consumers, who see the shape only through `AuroraRouter`.
- New permission key `storage:credentials:delete`; see step 10 above for operators running their own policy files.
- Files under `Ceph/Buckets/CredentialPrompt.*` moved to `Ceph/Credentials/`. Nothing outside the package imported them.

# Deliberately out of scope

- Naming or labelling keys. Keystone's credential object has no field for it — only `blob`, which we compose — and whether Keystone tolerates an extra key there is unverified against a real deployment. The limit stays at two until it is.
- Choosing which key the BFF signs with, and rotating by switching the active one. The choice is now deterministic, which is as far as this goes; there is still no "active" key, and the UI deliberately shows no such badge, because all of a user's keys map to one RGW identity.
- Swift, which does not use EC2 credentials.
