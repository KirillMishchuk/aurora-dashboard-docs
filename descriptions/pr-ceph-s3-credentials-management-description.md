# Summary

Gives Ceph/S3 users a place to see and manage their own access keys. Reported from `dashboard-aurora.eu-de-1.cloud.sap`, on the bucket list of a project that already had a working key:

> I have no option to see or manage my credentials.

There was no such screen. The only credentials UI in the product was `CredentialPrompt`, and `CephBuckets` rendered it on exactly one condition — `errorMessage === "NO_CEPH_CREDENTIALS"` — so a user who had a key could never reach it again. It was also the one place a secret was ever produced, and it never showed it: the `create` mutation already returned `{ access, secret }`, the component's `onSuccess` did not so much as declare the argument, invalidated the list and called `window.location.reload()`. The key went on working, but only inside Aurora. Anyone wanting to reach the same buckets with `aws s3`, s3cmd, rclone or a backup job had nothing to configure them with, and no way to rotate.

**The secret was recoverable all along.** Keystone's EC2 credentials are not Application Credentials: the secret is stored encrypted but decrypted on every read, so `GET /v3/credentials?user_id=…&type=ec2` returns a `blob` containing both halves, and the default `admin_or_owner` policy lets the owner read their own. Aurora's own BFF has relied on this since Ceph support landed — `resolveEC2Credential` (`middleware/resolveEC2Credential.ts`) performs that exact read on every Ceph request to sign the S3 call. Nothing new had to be exposed; the data was already crossing the BFF several times per page.

**Why a secret is fetched only at the moment it is revealed.** `type="password"` changes how an input paints a value it already holds — it is not a boundary. Filling every field as the modal opens would therefore put every key the caller holds into the DOM behind paint, on behalf of a user who most likely opened the modal to copy an endpoint. `handleRevealSecret` (`ManageCredentialsModal.tsx:234`) is the only place a secret is fetched and it hangs off that row's own Reveal — creating a key is no exception, and `create` does not return a secret at all, so there is no place in this modal where one appears unasked, so the cost is one request per key actually opened rather than one per key that exists; until then the field holds filler of the same length as a real secret (`SECRET_PLACEHOLDER`, `:40`), so it neither changes shape when the value arrives nor offers anything a reader of the DOM could mistake for a key. `handleHideSecret` (`:267`) throws the value away rather than flipping the input back over a live one, and so do deleting the key, `handleClose`, and a close that bypasses it (`:222`) — Escape reaches Juno's `Modal` through its focus trap's `escapeDeactivates`, a parent can drop `isOpen` on its own, and the modal stays mounted either way, so without that effect a secret revealed before such a close would still be on screen when it reopened. What none of this claims: a revealed secret *is* in React state and in the DOM, because Juno's `TextInput` is controlled and mirrors whatever it is handed into its own state. What is ours to decide is how long it stays there.

**Why the key you sign with was previously arbitrary.** `resolveEC2Credential` picked its credential with `.find()` over whatever order Keystone returned. With one key that is invisible. This PR lets a user hold several, so it became worth defining: the list is now sorted by credential `id` (`resolveEC2Credential.ts:63`) and the choice is stable across requests. EC2 credentials carry no timestamp, so this is deterministic rather than "most recent" — there is still no concept of an active key, and all of a user's keys map to one RGW identity anyway.

**Why one missing policy rule used to hide an entire domain.** `createPermissionRouter`'s `canUser` evaluates every requested key through `.map`, and `policy-engine` throws a plain `Error` when a rule is absent from the loaded file and that file has no `_default`. An uncaught throw therefore failed the whole batch — and `useCephPermissions` asks for ~20 keys in one call, so a single unknown rule hid every action in Ceph, not the one it governs. That is a reachable state and not only a mistake: `policyDir` is a consumer-supplied `createServer()` parameter, so operators run their own policy files, and a file written before a newly added key simply will not have that rule. Adding `storage:credentials:delete` would have walked straight into it. `checkSinglePermission` now catches that one failure per key and answers `false` for it alone (`createPermissionRouter.ts:154-168`); every other error still propagates, because answering "no permission" to a malformed rule expression would turn a real fault into a plausible-looking UI with no signal anywhere.

# Changes Made

## Server

- **`ec2CredentialRouter.ts`** — `create` returns `Ec2Credential`, not `Ec2CredentialWithSecret`: the secret is generated here and handed to Keystone, and the response carries only `{ id, access, user_id, project_id }`. The UI shows a new key concealed like any other and reads it through `reveal`, so a secret in this response would be a value crossing the wire that nothing consumes. This makes `reveal` the one procedure that ever hands a secret out.
- **`ec2CredentialRouter.ts`** — new `reveal` mutation (`:247`), returning `{ id, access, secret, user_id, project_id }` for one credential. A mutation and not a query on purpose: a query result lands in the TanStack Query cache and outlives the modal, visible in devtools until garbage collection, whereas a mutation result is never cached and is dropped by `reset()`.
- **`ec2CredentialRouter.ts`** — `fetchOwnedCredential`, shared by `reveal` and `delete`. The status the identity service answered with is the status the caller gets: 404 means "no such credential", 403 a permission problem, 401 an authentication one, nothing is rewritten into something else. That translation now lives in `rejectForIdentityStatus` and is reached from both shapes a refusal can arrive in — the rejected `SignalOpenstackApiError` a real client produces and a resolved non-ok response — and from both procedures that talk to Keystone, `delete`'s own DELETE call included. It previously existed only behind `if (!getResponse.ok)`, which `signal-openstack` never produces (`packages/signal-openstack/src/client.ts:194-207`), so a Keystone 403 reached the UI as an opaque 500 — and, on the delete path, as the text of a toast. What a 404 means is left to the two call sites, since it is an ordinary answer when reading a credential and a `NOT_FOUND` when deleting one; the one message that describes our own failure is passed in for the same reason — the client prints it verbatim in a toast, and a shared sentence would have a failed delete explain itself as a credential it could not read for verification, an operation that had already succeeded.
- **`ec2CredentialRouter.ts`** — the one answer the router decides for itself: a credential the identity service *does* return whose `user_id` or `project_id` is not the caller's. That happens under a permissive legacy policy, where deferring to the backend would mean handing over somebody else's secret, so it is refused instead — never parsed, never returned. Both ids come from the rescoped token, never from input, which is what makes this an authorization check rather than a filter the caller controls. The refusal stays `NOT_FOUND` rather than `FORBIDDEN` (#1182), though it conceals less than it appears to: `ctx.openstack` is the caller's own rescoped session, so the same request answers them the same way made directly against Keystone. Credentials of any other `type` are reported the same way a missing one is, rather than being deleted or parsed as an EC2 blob by a router that presents itself as S3 key management.
- **`ec2CredentialRouter.ts`** — `create` imposes no ceiling on how many credentials a user may hold, and reads nothing before posting. Neither Keystone nor RGW limits the count, and all of a user's keys in a project map to the same RGW identity, so an extra key grants no extra access and costs no quota — a limit here would only be this router refusing what the backend is willing to do. Dropping it also takes a `GET /credentials` off every creation.
- **`ec2CredentialRouter.ts`** — `delete` answers what the identity service said, and is deliberately *not* idempotent: a credential that is not there is `NOT_FOUND`, not a deletion reported as done. Folding it into success made the UI toast a key nobody deleted and hid the one case worth seeing — someone else removing that key while this screen was open. The 404 is caught where it actually arrives: `signal-openstack`'s `request()` rejects with `SignalOpenstackApiError` on every non-2xx instead of resolving with `ok: false` (`packages/signal-openstack/src/client.ts:194-207`), so the `if (!response.ok)` branch meant to handle it was unreachable and this would otherwise surface as an opaque 500. `NOT_FOUND` is also the answer for a credential owned by somebody else, so the two stay indistinguishable — the anti-enumeration property from #1182 is extended by this, not weakened.
- **`helpers/ec2CredentialMapper.ts`** — new. `toEc2Credential` / `toEc2CredentialWithSecret` replace the parse-and-validate block that stood three times in the router. Stricter than what it replaces: `"null"`, `"42"` and `"[]"` are valid JSON and used to reach the field reads, where `null` threw a `TypeError` the surrounding `try` swallowed by accident. Error messages name the credential id and nothing out of the blob.
- **`containerRouter.ts`** — `containers.status` returns `endpoint` and `region` alongside `hasCredentials` (`:37`). The S3 endpoint and region were known only to the server (`cephProcedure.ts`'s `resolveS3Config`) and appeared nowhere in the UI, which makes an access key on its own unusable. The procedure stays on `cephProcedure` rather than `cephProtectedProcedure` so Connection Details renders for a user who has no key yet.
- **`resolveEC2Credential.ts`** — sorts by `id` before choosing (`:63`), as above.
- **`policies/createPermissionRouter.ts`** — the per-key catch described in the summary. Matched on `policy-engine`'s message because the engine throws a plain `Error` and offers no way to ask whether a rule exists; logged at `warn` rather than `error`, since the docblock calls this a legitimate deployment state and ~20 keys are checked per page load.
- **`types/ceph.ts`** — `s3StatusSchema` gains `endpoint`/`region`; the four EC2 input schemas collapse into one `ec2CredentialIdInputSchema` used by both `reveal` and `delete`. Three of the four had no reference outside this file, `delete` re-declared its input inline, and the test suite was exercising the copy production never evaluated.
- **`routers/permissionRouter.ts`**, **`apps/dashboard/src/policies/storage.json`** — new permission key `storage:credentials:delete` → `storage:credential_delete`, viewer-tier for the same reason as `create`: managing one's own access keys is self-service, and Keystone enforces ownership independently.

## Client

- **`Ceph/Credentials/ManageCredentialsModal.tsx`** — new. **Access Keys** is a three-column `DataGrid` (`:408`): the access key ID in full, since Keystone's credential object carries no name or label and that string is the only way to tell two keys apart; the secret beside it; the delete button last. Both values sit in read-only `TextInput`s rather than clipboard controls — a value selects and copies out of an input perfectly well, so an icon would only have added a second way to do the same thing next to a field that already looked like one. The secret's field is an `InputGroup` (`:465`) carrying its own Reveal/Hide button, with `type` flipping between `password` and `text` and `readOnly` in both: the value is ours to show, not the user's to edit. Sizing is explicit rather than left to the grid, because the default squeezed the secret column below the 56 characters it has to hold and clipped the value: `gridColumnTemplate` with `min-content` floors (`:410`) instead of `minmax(0, …)`, and `min-w-[calc(57ch+2rem)]` / `min-w-[calc(41ch+2rem)]` on the fields themselves — `ch` is exactly one character wide under the `font-mono` they are set in, and the `+2rem` is Juno's own `px-4`, which border-box `min-width` would otherwise count as part of the 57. The modal is `size="xl"` (`:290`) for the same reason. Connection Details carries the endpoint and region, each copyable on its own. Creating a key adds its row with no page reload and concealed like every other one — `create` returns no secret to render — and a toast names the new access key and where to find it again. That second half is the useful one: the very first key in a project is created from the empty state by someone who has never seen this modal and reached it through a menu they had no reason to open, so without a pointer back the modal is found by accident and the secret looks like something that had to be caught at creation time. Deleting goes through `DeleteCredentialModal`, a confirmation dialog rendered inside this modal's own subtree — the shape `ObjectVersionHistoryModal` already uses to stack `DeleteVersionModal` over itself, which is the one existing modal-over-modal in the dashboard. It names the key and what is lost by it — and, when it is the only key left, adds that S3 Object Storage becomes unreachable in the dashboard as well as from outside clients, since the BFF signs every Ceph request with one of these credentials; the same paragraph says the buckets survive and a new key reaches them, which is true because all of a user's keys in a project map to one RGW identity. Prose rather than a `Message` banner: every confirmation dialog in the dashboard states its consequences in plain paragraphs, and a `Message` inside one means a failure that just happened. Confirming closes the dialog rather than holding it open for the request: Juno's `Modal` has no progress state for its confirm button, so staying open would swap the row spinner — the only feedback there is — for a frozen dialog. No type-the-word-to-confirm box, unlike `DeleteVersionModal`: an access key ID is 40 hex characters nobody will retype, and the damage is undone by creating another key. The row's button is labelled after its own key, since two rows otherwise offer two buttons reading "Delete Access Key" with nothing to tell them apart — and that label now belongs to the dialog. It carries its own `useModalTracking` under `storage.ceph.credentials.delete`, as every other confirmation dialog under `Ceph/` does — the parent's open/close says nothing about how often a delete is started and then abandoned. The outcome is a toast whichever way it goes — the deleted key on success, the identity service's own answer on failure — rather than the modal's error `Message`, so a delete reports itself in one place; the access key travels with the id being deleted rather than being looked back up in the credential list, which the same handler is invalidating and which can legitimately no longer hold it; and a failed delete still refreshes the key list, because the commonest failure is the key having been deleted elsewhere and leaving its row on screen would be a worse lie than the silent success this replaces.
- **`ManageCredentialsModal.tsx`** — one error surface, not one per row. A failed reveal is reported in the modal's single `Message` (`:301`), naming the access key it belongs to, rather than as that field's own `errortext`; nothing is recorded against the key, so the next Reveal is a plain retry, and the other key is untouched either way. `isBusy` (`:190`) deliberately excludes the secret fetches — those belong to one row, and gating Close/Create/Delete on them would put the whole modal behind one row's request — while `closeOnEsc={!isBusy}` (`:299`) does stop Escape running the close handler ahead of a pending create or delete, which the focus trap's `escapeDeactivates` would otherwise allow (it consults only `closeable`/`closeOnEsc` and ignores `disableCancelButton`/`disableCloseButton`). The implication does not run the other way: a create or delete in flight disables every control in the modal, Reveal included, since a reveal started against a row that is being deleted either reports `NOT_FOUND` for a key the user just removed or lands after the row is gone and leaves that secret in state for a credential that no longer exists. A completion that lands after a close is dropped rather than written back, and the test is which *opening* it belongs to (`openIdRef`, bumped on every change of `isOpen`) rather than whether one is open: "is the modal open" answers true again the moment it is reopened, so a reveal fired before a close would unmask its field in the next opening with nobody having clicked, and its `finally` would clear the spinner of whatever reveal that opening had started. Secrets live only in component state: `list` strips them server-side and `reveal` is a mutation, so nothing puts one in the query cache.
- **`Ceph/hooks/invalidateCredentialQueries.ts`** — new, third in the family after `invalidateBucketQueries` and `invalidateVersioningStatusQueries`. Refreshes the key table on every mutation and the bucket listing only when the project crosses between "no keys" and "at least one", which is the only transition `containers.list` reacts to — it is read with `includeMetadata: true`, the router's documented slow path, one `ListObjectsV2Command` per bucket in batches of five. The decision is taken from the cache *after* the credential list has been refreshed, not from the caller's copy: during a rotate the second mutation can settle before the first one's refetch lands, and a listing left in its `NO_CEPH_CREDENTIALS` error state with `retry: false` never refetches on its own. `containers.status` is deliberately not invalidated — its only reader takes two deployment constants from it under `staleTime: Infinity`, and each refetch would cost a Keystone credentials lookup in `cephProcedure`'s middleware.
- **`Ceph/Buckets/index.tsx`** — three entry points, all into the same modal: the overflow menu beside "Create Bucket" (`:329`), the rewritten empty state, and the "S3 Credentials No Longer Valid" screen (`:251`), which previously offered prose telling the user to create new credentials and nowhere to do it. The modal is mounted from a single unconditional return alongside `content` (`:226`, `:455`) rather than after the early returns, because deleting the last key from inside it flips the page underneath into the `NO_CEPH_CREDENTIALS` branch and the modal has to survive that transition instead of unmounting mid-operation.
- **`Ceph/Credentials/CredentialPrompt.tsx`** — moved here from `Ceph/Buckets/`, and no longer creates a credential or reloads the page; it opens the modal. Rebuilt on Juno's `Status`, the same component the bucket list's other full-page states are already made of, instead of hand-rolled markup. `status="empty"` and not `"error"` — holding no key yet is a starting point, not a failure — which also makes the container a `role="status"` rather than a `role="alert"`. `CredentialToastNotifications.tsx` holds both toasts, created and deleted.
- **`ManageCredentialsModal.tsx`** — an action nobody can take is not shown: "Create Access Key" and the row's delete button each render only for a user who may take them. One `Message` then names what is unavailable and sends them to an administrator — create, delete, or both in a single message — because a button that is simply absent reads as a feature this screen does not have. Only a *definite* no hides anything: while the check is in flight, or if it failed, both controls stay put and disabled, and the second case says "could not verify" rather than "you lack permission". The hook answers all-false until its query settles, so without that distinction the action column would start blank and sprout buttons a moment later. The key list, the endpoint and the region stay visible throughout; reading one's own keys is ungated, and a user who can only read is exactly who needs the endpoint and region.
- **`Ceph/hooks/useCephPermissions.ts`** — adds `canDeleteCredential` → `storage:credentials:delete` (`:68`). Reads stay ungated, per the hook's own docblock; only the two mutations are gated, and a failed permission *query* is now told apart from a denial, so a user is not advised to contact an administrator about access they already have.

# Behaviour and Contract Changes

- New procedure `storage.ceph.ec2Credentials.reveal`.
- `storage.ceph.ec2Credentials.delete` answers `NOT_FOUND` for a credential that is already gone, where it previously answered `{ success: true }`. A caller treating delete as fire-and-forget will now see an error for a key someone else removed first.
- `storage.ceph.ec2Credentials.create` no longer returns `secret`. The response is `{ id, access, user_id, project_id }`; the secret is read through `reveal`. Narrowing a contract, so worth a reviewer's eye — nothing in this package consumed the field, and consumers see the shape only through `AuroraRouter`.
- `storage.ceph.containers.status` returns two additional fields. Purely additive for consumers, who see the shape only through `AuroraRouter`.
- New permission key `storage:credentials:delete`; see step 10 above for operators running their own policy files.
- Files under `Ceph/Buckets/CredentialPrompt.*` moved to `Ceph/Credentials/`. Nothing outside the package imported them.

# Deliberately out of scope

- Naming or labelling keys. Keystone's credential object has no field for it — only `blob`, which we compose — and whether Keystone tolerates an extra key there is unverified against a real deployment. Until it is, two keys are told apart by their access key ID alone.
- Choosing which key the BFF signs with, and rotating by switching the active one. The choice is now deterministic, which is as far as this goes; there is still no "active" key, and the UI deliberately shows no such badge, because all of a user's keys map to one RGW identity.
- Keeping a revealed secret out of client memory altogether. Juno's `TextInput` is controlled and mirrors whatever it is handed into its own state, so a displayed secret is in React state and in the DOM regardless of who holds it. What this PR controls is lifetime — discarded on Hide, on delete and on close — not absence.
- Swift, which does not use EC2 credentials.
